## Основы git

По мере работы проект будет расти, игра будет развиваться, а, значит, встанет вопрос грамотной организации кода, чтобы с ним было удобно работать и его поддерживать в долгосрочной перспективе, особенно если над проектом работаете не одни. Стандартом такой организации работы с кодом является git - распредленная система контроля версий, которая позволяет сохранять определённые этапы работы с кодом в так называемые коммиты (**commits**), которые между собой образуют цепочку (историю / **history**) в рамках некоторой ветки разработки (**branch**). 

Как правило, каждая такая ветка создаётся для разработки какой-то функциональности (фичи / **feature**) вашего проекта  (например, написание класса Board - игрового поля), а коммиты в рамках этой ветки - отдельные маленькие законченные изменения в рамках реалиазации этой фичи (например, написание методов PutShipOnBoard(), TryCell() и тд). 

В любом git проекте есть одна главная ветка, называется **main** или **master**. В ней хранится финальная версия всего проекта, а остальные ветки, как только на них закончена работа (реализована нужная функциональность) вливаются в основную ветку (происходит слияние / **merge**).

Чтобы начать проект под git'ом, выполним команды в терминале Linux:
```
mkdir battleship
cd battleship
git init
```

Последняя команда делает ваш проект в директории `battleship` проектом под управление git. 

Создадим файлы `main.cpp` и `CMakeLists.txt`.

Введём первую важную команду `git status`.

Что она показывает: 

1) какие файлы у нас в проекте существуют, но которые не отслеживаются git'ом (**untracked files**); мы увидим только что два созданных файлы;

2) какие файлы у нас находятся в **индексе / staging area**; это такой буфер, который содержит в себе те файлы, которые мы собираемся включить в коммит; то есть это черновик коммита; сейчас у нас этот индекс пуст;

3) файлы, которые отслежиаются git'ом и которые были изменены сейчас, то есть они отличаются от состояния в предыдущем коммите; у нас таких файлов нет, потому что мы не создали до этого ещё ни одного коммита;

Вообще все файлы нашего проекта, как отслеживаемые, так и не отслеживаемые git'ом, образуют **working tree**.

Пусть у нас два файла на данный момент образуют первую версию проекта, тогда мы можем создать первый коммит:
```
git add main.cpp
git add CMakeLists.txt
```
Тем самым мы добавили эти файлы в staging area.

После этого создадим коммит из файлов, добавленный в staging area:
```
git commit -m "Init commit"
```

Через флаг `-m` мы пишем сообщение коммита - краткое и ёмкое, которое отражает суть коммита (обычно первый коммит принято называть Init commit, а так пишут по факту, например, `implement class Board`).

Можем теперь посмотреть дерево коммитов:

`git log`

Более компактный вывод:

`git log --oneline`

Далее добавим в `main.cpp` структуру `Cell`. Введём команду `git diff`, увидим, какие строки мы добавили / изменили в `main.cpp` по сравнению с состоянием этого файла в последнем коммите. Если мы хотим откатиться к исходному состоянию `main.cpp`, то вводим `git restore main.cpp`.

Давайте для демонстрации работы git'а создадим отдельную ветку `cell_branch`, в которой напишем структуру `Cell` и после чего вольём эту ветку в нашу основную`main` и удалим `cell_branch`:

```
git restore main.cpp
git switch -c cell_branch
[меняем main.cpp]
git add main.cpp
git commit -m "implement struct Cell"
git switch main
git merge cell_branch
git branch -D cell_branch
git log
```

Вместо `git switch -c cell_branch` можно писать `git checkout -b cell_branch`. После этого мы переключимся на новую ветку (посмотреть список веток можно командой `git branch`). Последняя команда `git log` покажет нам новый коммит, который появился в ветке `main` в результате слияния ветки `cell_branch` и `main`.

Чтобы про наш проект узнал мир или, например, коллеги по разработке, надо его опубликовать. Существует `GitHub` - сеть серверов для публикации кода. Каждый пользователь сервиса под своим аккаунтом публикует свои проеты в **репозиториях**. Чтобы опубликовать свой проект на GitHub, нужно:

- завести аккаунт: https://github.com/
- нажать кнопку `New` на вкладке `Repositories` и создать новый репозиторий: ввести имя проекта, можно описание, остальное пока не нужно
- после зайти в только что созданный репозиторий, нажать кнопку `<>Code`, скопировать SSH ссылку на репозиторий и добавить её локально в свой проект:

```
git remote add origin url
```
`origin` - локальное имя удалённого репозитория
`url` - SSH адрес репозитория

- отправить свой проект на сервер:
```
git push -u origin main
```
Здесь `main` - имя главной ветик на удалённом сервере

Теперь проект появится на GitHub.

Если надо скачать (склонировать) какой-либо проект себе локально, то:
```
git clone url
```

По коммитам можно перемещаться, то есть откатываться назад по истории:
```
git switch hash
```

где `hash` - хеш коммита - 16ричное число, которое можно увидеть после `git log`.

Чтобы вернуться на самый новый коммит, введите `git switch your_branch`, где `your_branch` - имя ветки, на которой работаете. 

Для лучшего освоения git'а стоит изучить команду `git rebase -i` - интерактивный rebase - мощный инструмент, который позволяет менять историю коммитов.
